# crito-api

Общая headless-CMS для корпоративных сайтов, которые собираются из готовых блоков. Редактор правит контент и собирает страницы в админке без релиза. Разработчик добавляет новые блоки и макеты в коде.

Первый подключённый проект — **RuCode**. Архитектура рассчитана на несколько проектов с общими блоками и собственными темами.

## Основные понятия

| Понятие | Что это |
|---|---|
| **Проект** | Отдельный сайт со своим набором страниц, манифестом блоков, ключами шапки/футера и темой |
| **Страница** | Slug, SEO, ключ шапки и футера, список блоков. Главная хранится как `/index` |
| **Блок** | Экземпляр компонента на странице |
| **Манифест** | Список типов блоков проекта с их схемами. Публикуется из CI при деплое фронтенда |
| **Схема блока** | Описание данных блока (zod на фронтенде → JSON Schema на бэкенде). Есть схема — блок редактируемый |
| **Версия** | Каждое сохранение страницы создаёт новую версию и сразу публикуется. Черновиков нет |

## Возможности

### Для редактора
- Правка содержимого блоков, у которых описана схема (формы строятся из манифеста): тексты, списки, числа, переключатели, ссылки, изображения из медиатеки, rich-text.
- Включение, скрытие и перестановка любых блоков (кнопками «выше/ниже»). Якоря для ссылок вида `/#anchor`.
- SEO страницы: title, description, og-заголовок, og-описание, og-картинка.
- Создание страниц: адрес и заголовок, остальное в редакторе.
- **Мягкое удаление.** Удалённая страница уходит в корзину: пропадает с сайта и из списка, но хранится вместе с историей. Из корзины её можно восстановить (в прежнем состоянии) или удалить навсегда. Сразу после удаления можно нажать «Отменить». Адрес остаётся занятым, пока страница в корзине. Все эти действия доступны при доступе ко всему проекту.
- Медиатека: загрузка (кнопкой и перетаскиванием), поиск, копирование ссылки, удаление (файл, который используется на страницах, в том числе из корзины, удалить нельзя).
- **Главная** (`/`): карточки проектов, к которым есть доступ: название, число страниц, дата последнего изменения, уровень доступа («Весь проект» или «Отдельные страницы»). Тому, у кого права только на отдельные страницы, карточка показывает и считает только их, а список страниц проекта содержит только их. Единственный проект открывается сразу, кроме администратора админки.
- **Справочники** (боковое меню, рядом с проектами, не внутри проекта). Сейчас один: «Регионы» (список регионов РФ для формы участия): поиск, добавление, правка, удаление, порядок числом. Справочник **общий для всех проектов**: его читает любой вошедший пользователь, **правит только администратор админки** (доступ ко всему проекту не даёт права правки, чтобы редактор одного сайта не ломал остальные). Каждое изменение вызывает вебхуки всех проектов.
- История версий и откат (откат создаёт новую версию). Защита от одновременной правки: если страницу успели сохранить, редактор увидит конфликт, а не затрёт чужие изменения.
- Публикация сразу после сохранения: кэш сайта сбрасывается вебхуком (без вебхука — по TTL, около 60 секунд).

### Для сайта
- Страницы берутся из CMS. При ошибке (недоступность, таймаут, невалидный ответ) используются локальные данные из `*.data.ts`.
- Справочник регионов отдаётся по `GET /public/dictionaries/regions` массивом `{ value, label }` в заданном порядке; он общий для всех проектов. Форма совпадает с `RegionOption` сайта: достаточно заменить зашитый `RUSSIAN_REGIONS` ответом API. Кэш и `ETag` как у страниц. Старый адрес `/public/:project/dictionaries/regions` работает и отдаёт то же самое (для уже выложенных сайтов).
- Страницы без записи в CMS продолжают работать на локальных данных, поэтому подключать их можно по одной.
- Страницы, созданные в админке, открываются по своему slug. Любой адрес, которого нет в CMS (включая заведомо невалидные: заглавные буквы, точки, пробелы, кириллицу), отдаёт 404.
- Публичный ответ кэшируется только с проверкой `ETag` (`Cache-Control: public, no-cache`): публикация видна сразу.
- Rich-text очищается на сервере при сохранении и повторно на стороне сайта; секрет вебхука шифруется в БД; токены не попадают в браузер.

### Для разработчика
- Каталог блоков и формы админки строятся из манифеста. Под новый блок бэкенд и админку дорабатывать не нужно.
- Бэкенд валидирует данные блоков по JSON Schema и не публикует страницы с неизвестным `type`.
- Чтобы сделать блок редактируемым, достаточно описать его схему во фронтенде.
- Общий контракт типов между API, админкой и сайтами: [`packages/contract`](#контракт).

## Архитектура

Монорепо на npm workspaces:

```
crito-api/
  apps/
    api/             Nest 12 + Prisma 7 + PostgreSQL: CMS, права, медиа, публичное чтение
    admin/           Nuxt 4 + Nuxt UI (SPA): редактор страниц и медиатека
  packages/
    contract/        @crito/contract: типы данных между API, админкой и сайтами
  scripts/rucode/    экспорт контента сайта rucode в JSON для импорта в CMS
  docker-compose.yml Postgres для разработки
```

```
 редактор ──▶ админка (Nuxt, /cms-api/**) ──прокси──▶ API ──▶ PostgreSQL
                                                       │  └─▶ хранилище файлов (диск)
 CI сайта ──PUT манифест (x-ci-key)────────────────────┤
 сайт ◀──GET /public/<project>/pages/<slug>────────────┘
 сайт ◀──POST вебхук сброса кэша (x-revalidate-secret)── API (после публикации, в фоне)
```

**Данные** (Prisma): `Project` (настройки, манифест, хеш ключа CI, зашифрованный секрет вебхука), `Page` (текущее содержимое и версия; у удалённой страницы заполнено `deletedAt`), `PageRevision` (снимок каждого сохранения), `Media` (метаданные файла; сам файл в хранилище), `User` (зеркало пользователя LMS: паролей нет).

### API

Админские методы требуют сессию (`Authorization: Bearer`). Открыты только помеченные «публично».

| Метод | Адрес | Доступ |
|---|---|---|
| GET | `/health` | публично: живость и доступность БД |
| GET | `/public/:project/pages/*` | публично: страница в формате `ContentPage` |
| GET | `/public/dictionaries/regions` | публично: общий справочник регионов, массив `{ value, label }` в заданном порядке |
| GET | `/public/:project/dictionaries/regions` | устаревший адрес того же справочника (404 для неизвестного проекта) |
| GET | `/me` | кто вошёл: `email`, `name`, `isSuperAdmin` |
| GET | `/media/:project/:sha256.:ext` | публично: файл (кэш на год, `nosniff`) |
| GET, POST | `/projects` | список доступных проектов; создание (суперадмин) |
| GET, PATCH | `/projects/:project` | проект; настройки, секрет вебхука и номер счётчика Яндекс Метрики `metrikaCounterId` (суперадмин; цифры, до 12 знаков; пустая строка очищает). Номер видят все с доступом к проекту, в публичный API он не попадает |
| POST | `/projects/:project/ci-key` | новый ключ CI (суперадмин) |
| GET | `/projects/:project/manifest` | манифест блоков |
| PUT | `/projects/:project/manifest` | загрузка манифеста: заголовок `x-ci-key`, без сессии |
| GET, POST | `/projects/:project/pages` | список (только доступные страницы, без корзины); создание (право на весь проект) |
| GET | `/projects/:project/pages/trash` | корзина: удалённые страницы с автором и датой удаления (право на весь проект) |
| GET, PUT, DELETE | `/projects/:project/pages/:id` | страница; сохранение = публикация (удалённую сохранять нельзя, 409); удаление в корзину (право на весь проект) |
| POST | `/projects/:project/pages/:id/restore` | вернуть страницу из корзины (право на весь проект) |
| DELETE | `/projects/:project/pages/:id/purge` | удалить из корзины навсегда вместе с историей (право на весь проект, только для страницы из корзины) |
| GET | `/projects/:project/pages/:id/revisions` | история версий |
| POST | `/projects/:project/pages/:id/revisions/:version/restore` | откат (создаёт новую версию) |
| GET, POST | `/projects/:project/media` | список с поиском; загрузка (`multipart`, поле `file`) |
| DELETE | `/projects/:project/media/:id` | удаление, если файл нигде не используется |
| GET, POST | `/dictionaries/regions` | общий справочник регионов: список по порядку (любой вошедший); добавление (`value` уникален глобально, иначе 409; суперадмин) |
| PATCH, DELETE | `/dictionaries/regions/:id` | правка (`label`, `value`, `sortOrder`); окончательное удаление (суперадмин). Изменения вызывают вебхуки всех проектов |

В разработке документация доступна на `/docs` (Swagger).

## Быстрый старт (локальный запуск)

**Нужно:** Node.js 22+ (npm идёт в комплекте), Docker (для PostgreSQL; можно и свой PostgreSQL, тогда укажите его в `DATABASE_URL`), git. На Windows команды ниже работают в PowerShell и Git Bash.

```bash
# 1. Зависимости. Заодно генерируется Prisma-клиент (postinstall)
npm install

# 2. База данных (PostgreSQL 17 в Docker, порт 5432, пользователь/пароль/база: crito)
npm run db:up

# 3. Настройки API
cp apps/api/.env.example apps/api/.env          # PowerShell: Copy-Item apps/api/.env.example apps/api/.env
#    откройте apps/api/.env и поставьте AUTH_DEV_BYPASS=true (см. «Вход» ниже)

# 4. Таблицы
npm run db:migrate

# 5. Запуск (в двух терминалах; API запускайте первым)
npm run api                                      # API: http://localhost:3000, Swagger: http://localhost:3000/docs
npm run admin                                    # админка: http://localhost:3100
```

**Вход.** Вход через LMS ещё не реализован, поэтому локально без флага `AUTH_DEV_BYPASS=true` все админские методы отвечают 401. С флагом все запросы идут от локального суперпользователя. Флаг работает только при `NODE_ENV=development`; dev-команды (`npm run api`) выставляют его сами.

**Первый проект.** Админка показывает проекты из БД, а в чистой базе их нет. Создайте проект и получите ключ CI (он показывается один раз):

```bash
curl -X POST http://localhost:3000/projects -H "content-type: application/json" \
  -d '{"slug":"rucode","name":"RuCode"}'
# PowerShell: используйте curl.exe и одинарные кавычки вокруг JSON, либо Swagger UI на /docs
```

На сервере, где войти в админку нельзя, проект создаётся из консоли тем же способом, что и импорт страниц (ключ CI печатается один раз):

```bash
npm run build -w @crito/api
npm run create-project -- --slug rucode --name RuCode [--revalidate-url https://site/api/revalidate --revalidate-secret <секрет>] [--metrika-counter-id 12345678]
```

**Манифест блоков.** Без манифеста страницы нельзя создавать и сохранять. Соберите его во фронтенде сайта (`npm run manifest`, файл `.output/manifest.json`) и отправьте:

```bash
curl -X PUT http://localhost:3000/projects/rucode/manifest \
  -H "x-ci-key: <ключ CI из ответа выше>" -H "content-type: application/json" \
  --data-binary @.output/manifest.json
```

**Каталог блоков в админке.** Окно «Добавить блок» строится по манифесту. Необязательные поля блока управляют каталогом (старые манифесты работают без них):

| Поле | Назначение |
|---|---|
| `origin` | `library` — универсальный блок UI-библиотеки (вкладка «Библиотека UI»); иначе блок проекта |
| `group` | раздел или событие для боковой навигации («AI Champ»); без поля берётся из скобок в названии, иначе категория |
| `description` | подпись на карточке |
| `preview` | картинка-превью на карточке |
| `pages` | маски адресов страниц, где блок рекомендован (`/ai-champ/*`); влияет на вкладку «Для этой страницы» |

Вкладка «Для этой страницы» показывает блоки, чья маска `pages` подходит странице, уже стоящие на ней и (при пустом `pages`) однотипные по префиксу типа (`aiChamp.*`). Вкладка «Библиотека UI» появляется, только если есть блоки с `origin: 'library'`. Последние добавленные блоки запоминаются в браузере по проектам. Shift + клик добавляет блок и оставляет окно открытым.

После этого откройте http://localhost:3100: появятся проект, медиатека и редактор страниц. Чтобы перенести в CMS существующие страницы сайта rucode, см. [Миграцию контента](#миграция-контента-rucode). Чтобы сайт читал страницы из локальной CMS, задайте ему `NUXT_CMS_BASE_URL=http://localhost:3000/public/rucode`.

**Частые проблемы**
- *Админка пишет «Нет доступа» или «Не удалось загрузить»*: API не запущен или в `.env` не включён `AUTH_DEV_BYPASS=true`.
- *API не стартует с ошибкой про `SESSION_SECRET`/`SECRETS_KEY`*: он запущен не dev-командой и не видит `NODE_ENV=development`. Используйте `npm run api` или добавьте `NODE_ENV=development` в `.env` (в `.env.example` он уже есть).
- *Порт 3000 занят внутренним сервером Nuxt*: запускайте API раньше админки.
- *Ошибка подключения к БД*: `npm run db:up` не запущен (или не запущен Docker Desktop).
- *Сбросить всё*: `docker compose down -v` (удалит данные локальной БД), затем шаги 2 и 4 заново.

Остановить базу: `npm run db:down`.

## Конфигурация

### API (`apps/api/.env`)

| Переменная | Назначение |
|---|---|
| `NODE_ENV` | `development` включает режим разработки. **Любое другое значение, включая пустое, это боевой режим** со строгой проверкой конфигурации |
| `PORT` | Порт API (по умолчанию 3000) |
| `DATABASE_URL` | Подключение к PostgreSQL. Обязательна всегда |
| `PUBLIC_BASE_URL` | Публичный адрес API, например `https://cms.example.ru`. Попадает в ссылки на файлы внутри страниц, поэтому задавать сразу правильный. Обязательна в боевом режиме |
| `SESSION_SECRET` | Секрет подписи сессий, не короче 32 символов. Обязателен в боевом режиме |
| `SECRETS_KEY` | Ключ шифрования секретов в БД: 32 байта в base64 или 64 hex-символа. Обязателен в боевом режиме |
| `AUTH_DEV_BYPASS` | `true` открывает доступ без входа от имени локального суперпользователя. Только `NODE_ENV=development` |
| `ADMIN_TOKEN` | Необязателен. Служебный токен до появления входа через LMS: Bearer-запрос с ним выполняется от суперадмина. Не короче 32 символов. Его подставляет прокси админки (`NUXT_ADMIN_TOKEN`), в браузер он не попадает. **Админка при этом обязана быть закрыта на уровне nginx** |
| `HOST` | Адрес, на котором слушает API. На проде `127.0.0.1`; без значения слушает все адреса |
| `STORAGE_DRIVER` | Хранилище файлов: пока только `local` |
| `STORAGE_LOCAL_DIR` | Каталог файлов. Относительный путь считается от `apps/api`, а не от папки запуска; на проде лучше абсолютный |
| `LMS_*` | Зарезервированы под вход через LMS, пока не используются |

Сгенерировать ключи: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`.

### Админка (`apps/admin`)

| Переменная | Назначение |
|---|---|
| `NUXT_API_URL` | Адрес API для прокси `/cms-api/**`. **Читается при запуске, а не при сборке**: одна сборка работает в любом окружении. По умолчанию `http://localhost:3000` |
| `NUXT_ADMIN_TOKEN` | Тот же `ADMIN_TOKEN`, что у API. Прокси подставляет его в запросы к API вместо заголовка браузера. Только на сервере |
| `NUXT_APP_BASE_URL` | Префикс адреса админки, например `/admin/`. **Задаётся при сборке** (влияет на адреса ассетов) и дублируется при запуске. Под Git Bash на Windows добавьте `MSYS_NO_PATHCONV=1`, иначе `/admin/` превратится в путь Git |

Браузер обращается к API через тот же origin (`/cms-api/**`), поэтому CORS и общие cookie между доменами не нужны.

## Безопасность

- **Закрыто по умолчанию.** Глобальный guard требует сессию на всех методах, кроме явно помеченных `@Public()` (публичное чтение страниц и файлов, `/health`, загрузка манифеста по ключу CI).
- **Боевой режим строгий.** Если `NODE_ENV` не равен `development` (или `test`), приложение не стартует без `SESSION_SECRET`, `SECRETS_KEY`, `PUBLIC_BASE_URL` и отказывается принимать `AUTH_DEV_BYPASS=true`; Swagger выключен. Забытая переменная окружения не открывает небезопасных значений по умолчанию. Сообщение об ошибке перечисляет все проблемы сразу.
- **Права.** Права выдаются в LMS и приходят в сессии: на весь проект или на отдельные страницы (`Grant` в контракте). Ролей нет, редактирование включает публикацию. Доступ к отдельным страницам не позволяет создавать и удалять страницы, пользоваться корзиной, менять проект и ключи, удалять файлы; удалённой страницы такой редактор не видит. Ответы про проект содержат `fullAccess`: по нему админка скрывает недоступные действия.
- **Сессии.** Короткие (15 минут), подписаны `SESSION_SECRET`. Выдача сессии через обмен токена LMS ещё не реализована.
- **Секреты в БД.** Секрет вебхука хранится зашифрованным (AES-256-GCM, формат `v1:<iv>:<tag>:<данные>`), значение привязано к своему полю и в API не возвращается. Ключ CI хранится только хешем SHA-256 и показывается один раз.
  - **Потеря или смена `SECRETS_KEY` делает сохранённые секреты нечитаемыми.** Храните ключ отдельно от БД и её бэкапов. Если ключ сменился, задайте секрет заново: `PATCH /projects/:project` с `{ "revalidateSecret": "..." }`.
  - Записи без префикса `v1:` (созданные в разработке без ключа) читаются как открытый текст и шифруются при следующем сохранении.
- **Очистка данных блоков.** Перед записью страницы (создание, сохранение, откат, импорт) сервер обходит данные блока по его JSON Schema:
  - строки с `x-field: richtext` очищаются от опасного HTML; разрешены `p, br, b, strong, i, em, u, s, a, span, ul, ol, li, blockquote, h1–h6, code, pre, hr` и атрибуты `href, target, rel, class`; ссылкам с `target="_blank"` добавляется `rel="noopener noreferrer"`;
  - в полях `x-field: link` и `x-field: image` допустимы только относительные адреса, `http`, `https`, `mailto`, `tel`;
  - **очищаются только поля, помеченные в схеме.** Если поле хранит HTML, во фронтенде его нужно объявить как `richText()`, а не `text()`;
  - содержимое блоков без схемы (`readonly`) сервер проверить не может, поэтому редактор с доступом только к отдельным страницам не может его менять (только показывать, скрывать, переставлять). При доступе ко всему проекту это разрешено.
- **Файлы.** Тип определяется по содержимому, а не по расширению; лимиты 10 МБ (изображения), 1 МБ (SVG), 20 МБ (PDF); у JPEG удаляется EXIF; SVG со `script`, `foreignObject`, `iframe` отклоняются, остальное очищается, отдаётся с CSP `sandbox`; имя файла в хранилище это SHA-256 содержимого.
- **HTTP.** Заголовки helmet (в том числе скрыт `X-Powered-By`), лимит JSON-тела 5 МБ, публичные ответы с `ETag`.
- **Вебхук сайта** вызывается в фоне и не задерживает сохранение. При остановке сервера (`SIGTERM`) незавершённые вызовы дожидаются.

## Развёртывание (продакшен)

> **Вход через LMS ещё не реализован**, а обход входа (`AUTH_DEV_BYPASS`) в боевом режиме запрещён. До его появления админка работает так: `ADMIN_TOKEN` на сервере плюс **basic auth в nginx** перед админкой (прокси админки сам подставляет токен). Все, кто прошёл nginx, работают как суперадмин, автор правок в истории один («Администратор»), выдать права отдельным редакторам нельзя. Готовый вариант для сервера, где уже стоит сайт под pm2 и nginx (админка по `/admin`, API по `/cms-api`), описан в [`deploy/README.md`](deploy/README.md). Ниже общая схема на systemd. Готовых `Dockerfile`/compose нет (см. [TODO](#todo)), файлы хранятся на диске сервера (S3 не подключён).

### Что нужно

| Компонент | Требование |
|---|---|
| Сервер | Linux x64 (проверялась Windows-разработка; `sharp` и `jsdom` ставятся prebuilt под платформу, поэтому `npm ci` выполняйте **на целевой платформе**) |
| Node.js | 22+ |
| PostgreSQL | отдельная БД и пользователь для CMS (в разработке используется 17); порт БД наружу не открывать |
| Диск | постоянный каталог под файлы медиатеки (`STORAGE_LOCAL_DIR`), его нужно бэкапить |
| Домены и TLS | два адреса: API (например, `cms-api.example.ru`) и админка (`cms.example.ru`), оба по HTTPS через обратный прокси |
| Секреты | `SESSION_SECRET`, `SECRETS_KEY` (генерация в разделе [Конфигурация](#конфигурация)), хранить вне репозитория и вне бэкапов БД |
| Сайты | у каждого сайта: `NUXT_CMS_BASE_URL`, приём вебхука сброса кэша, шаг CI с отправкой манифеста (см. [Подключение сайта](#подключение-сайта)) |

### Порядок развёртывания

```bash
# 1. На сервере: код и зависимости (postinstall генерирует Prisma-клиент, DATABASE_URL для этого не нужен)
git clone <репозиторий> /opt/crito && cd /opt/crito
npm ci

# 2. Сборка API и админки
npm run build

# 3. Миграции (с боевым DATABASE_URL в окружении или в apps/api/.env). Выполняются при каждом обновлении
npm run db:migrate

# 4. Запуск процессов (см. systemd ниже)
NODE_ENV=production node apps/api/dist/main                                   # API, порт 3000
NUXT_API_URL=http://127.0.0.1:3000 NITRO_HOST=127.0.0.1 NITRO_PORT=3100 \
  node apps/admin/.output/server/index.mjs                                    # админка, порт 3100
```

Адрес API админки (`NUXT_API_URL`) читается **при запуске**: одну сборку можно запускать в разных окружениях. Приложение само проверяет конфигурацию при старте и не запустится, если чего-то не хватает: в сообщении перечислены все проблемы сразу.

### Окружение API (пример `/etc/crito/api.env`)

```ini
NODE_ENV=production
PORT=3000
DATABASE_URL=postgresql://crito:<пароль>@127.0.0.1:5432/crito?schema=public
PUBLIC_BASE_URL=https://cms-api.example.ru
SESSION_SECRET=<64 hex-символа>
SECRETS_KEY=<32 байта в base64>
STORAGE_DRIVER=local
STORAGE_LOCAL_DIR=/var/lib/crito/uploads
```

`PUBLIC_BASE_URL` попадает в ссылки на файлы **внутри сохранённых страниц**: задавайте сразу итоговый публичный адрес, позже менять его значит мигрировать данные. `AUTH_DEV_BYPASS` на проде не задавайте вообще.

### Процессы (systemd)

`/etc/systemd/system/crito-api.service`:

```ini
[Unit]
Description=Crito CMS API
After=network.target postgresql.service

[Service]
User=crito
WorkingDirectory=/opt/crito/apps/api
EnvironmentFile=/etc/crito/api.env
ExecStart=/usr/bin/node dist/main
Restart=always

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/crito-admin.service`:

```ini
[Unit]
Description=Crito CMS admin
After=crito-api.service

[Service]
User=crito
WorkingDirectory=/opt/crito/apps/admin
Environment=NITRO_HOST=127.0.0.1 NITRO_PORT=3100 NUXT_API_URL=http://127.0.0.1:3000
ExecStart=/usr/bin/node .output/server/index.mjs
Restart=always

[Install]
WantedBy=multi-user.target
```

При остановке (`SIGTERM`) API дожидается незавершённых вызовов вебхуков и закрывает соединение с БД.

### Обратный прокси (nginx)

Нужны **два сервера** и увеличенный лимит тела: по умолчанию nginx принимает 1 МБ, а файлы загружаются до 20 МБ.

```nginx
server {
    listen 443 ssl;
    server_name cms-api.example.ru;          # API: публичное чтение страниц и файлов сайтами, админские запросы
    client_max_body_size 25m;
    location / { proxy_pass http://127.0.0.1:3000; proxy_set_header Host $host; }
}

server {
    listen 443 ssl;
    server_name cms.example.ru;              # админка (SPA + прокси /cms-api/** к API)
    client_max_body_size 25m;
    location / { proxy_pass http://127.0.0.1:3100; proxy_set_header Host $host; }
}
```

Админку (`cms.example.ru`) стоит дополнительно закрыть от публичного доступа (VPN, IP-фильтр) до появления входа через LMS. Для файлов (`/media/...`) можно поставить CDN перед API: имя файла содержит хеш содержимого, поэтому кэшировать можно бессрочно.

### Что бэкапить

- **БД:** `pg_dump -Fc crito > crito-$(date +%F).dump` (ежедневно, с хранением нескольких копий; восстановление проверьте на отдельном сервере).
- **Файлы:** весь `STORAGE_LOCAL_DIR`: в БД лежат только метаданные, без каталога файлов страницы потеряют картинки.
- **`SECRETS_KEY`:** отдельно и в надёжном месте. Без него сохранённые секреты (вебхуки сайтов) не расшифровать, их придётся задать заново.

### Обновление версии

```bash
cd /opt/crito && git pull && npm ci && npm run build && npm run db:migrate
sudo systemctl restart crito-api crito-admin
```

Миграции в основном добавляют колонки и таблицы, но бывают и изменения типов (так было с хранением манифеста): прочитайте новые файлы в `apps/api/prisma/migrations` перед применением и сделайте бэкап БД. Порядок «миграция, затем перезапуск» безопасен для добавляющих миграций.

### Проверка после запуска

1. `curl https://cms-api.example.ru/health` отвечает `{"status":"ok","database":"up"}` (его же используйте в мониторинге).
2. `curl -i https://cms-api.example.ru/projects` даёт 401 (закрыто по умолчанию); `/docs` даёт 404 (Swagger выключен).
3. `curl https://cms-api.example.ru/public/<проект>/pages/index` даёт 200 или 404, но не 5xx; в заголовках нет `X-Powered-By`.
4. Загрузка файла больше 1 МБ проходит (проверка лимитов прокси).
5. Сайт читает страницы по `NUXT_CMS_BASE_URL`, а после сохранения страницы вебхук сбрасывает его кэш.

## Подключение сайта

- Сайт читает страницы по адресу `NUXT_CMS_BASE_URL=<api>/public/<project>` (запрос `/pages/<slug>`, главная как `/index`).
- Вебхук сброса кэша: сайт принимает `POST` с заголовком `x-revalidate-secret`; адрес и секрет задаются в проекте (`PATCH /projects/:project`, поля `revalidateUrl` и `revalidateSecret`).
- Счётчик Яндекс Метрики: номер задаёт разработчик (`PATCH /projects/:project` с `metrikaCounterId` или `--metrika-counter-id` при создании). В админке он показан менеджерам справкой (копирование и ссылка на Метрику) в списке страниц и в настройках страницы, без редактирования. Сам счётчик на сайте подключается кодом сайта; публичный API номер не отдаёт.
- Манифест блоков собирает фронтенд (`npm run manifest`) и отправляет в CI после деплоя: `PUT /projects/:project/manifest` с заголовком `x-ci-key`. Без манифеста страницы нельзя создавать и сохранять.
- Формат страницы совпадает с `ContentPage` фронтенда rucode.

## Миграция контента rucode

Локальный контент страниц сайта (`src/pages/*/model/*.data.ts`) переносится в БД двумя шагами. Фронтенд при этом не меняется.

```bash
# 1. Экспорт: берёт данные из фронтенда его же реестром блоков (алиасы типов, миграции схем)
npm run export:rucode -- --front <путь к репозиторию фронтенда> --out scripts/rucode/pages.json

# 2. Импорт: проверяет каждую страницу по манифесту проекта и записывает в БД
npm run build -w @crito/api
npm run import:pages -- --file scripts/rucode/pages.json --project rucode --dry-run   # только проверка
npm run import:pages -- --file scripts/rucode/pages.json --project rucode
```

- Проект должен существовать, а манифест блоков быть загружен (иначе импорт остановится с подсказкой).
- Импорт запускает то же приложение, поэтому на него действует та же проверка конфигурации. На сервере это боевое окружение API; локально задайте `NODE_ENV=development` (PowerShell: `$env:NODE_ENV='development'`, bash: `NODE_ENV=development npm run import:pages ...`), иначе он потребует `SESSION_SECRET`, `SECRETS_KEY` и `PUBLIC_BASE_URL`.
- Повторный запуск безопасен: существующие страницы пропускаются. Страница в корзине импортом не затрагивается (адрес занят): восстановите или удалите её навсегда вручную. Флаг `--overwrite` записывает данные как новую версию.
- Импорт ходит в БД напрямую, без входа: запускайте его на сервере оператором. Данные проходят ту же очистку, что и сохранение из админки.
- Сайт сам переключится на CMS: `usePageContent` берёт страницу из CMS, а локальные данные остаются запасным вариантом. Когда CMS проверена, локальные `*.data.ts` можно удалять постранично.
- Картинки и видео остаются на путях сайта (`/images/...`, `/videos/...`), в медиатеку они не переносятся.
- Страницы читаются из CMS только на языке по умолчанию (`ru`); английская версия `/champ` продолжает браться из локальных данных.

**Справочник регионов.** Начальный список (90 регионов из `src/shared/config/regions.ts` сайта) лежит в `scripts/rucode/regions.json`. Загрузка тем же приложением, после `npm run build -w @crito/api`:

```bash
npm run import:regions -- --file scripts/rucode/regions.json --dry-run   # только проверка
npm run import:regions -- --file scripts/rucode/regions.json
```

Справочник общий для всех проектов, поэтому проект не указывается. Порядок регионов в файле становится порядком справочника. Повторный запуск безопасен: существующие регионы (по `value`) пропускаются, правки из админки не теряются; `--overwrite` перезаписывает названия и порядок. После записи вызываются вебхуки всех проектов. На сайте остаётся заменить `RUSSIAN_REGIONS` запросом к `/public/dictionaries/regions` (с локальным списком как запасным вариантом).

> Миграция `global_regions` делает справочник общим: убирает привязку региона к проекту. Если у разных проектов были регионы с одним `value`, остаётся самая ранняя запись, остальные удаляются.

## Тесты и проверки

```bash
npm test             # юнит-тесты API и админки (БД не нужна)
npm run typecheck    # контракт, API (вместе со сверкой контракта) и админка
npm run db:up        # для e2e нужен запущенный Postgres
npm run test:e2e     # e2e: настоящее приложение и БД, вход без обхода
```

e2e работают только с отдельной БД `crito_e2e` на том же сервере Postgres: она создаётся перед прогоном (с миграциями) и удаляется после, рабочая БД из `apps/api/.env` не затрагивается. Служебное подключение для создания БД переопределяется переменной `E2E_ADMIN_DATABASE_URL`.

Сценарии e2e: закрытость по умолчанию и подделка токенов, проекты и шифрование секрета, манифест и ключ CI, жизненный цикл страниц (версии, конфликты, откат, вебхук), корзина (удаление, восстановление, окончательное удаление, права, занятый адрес, файлы страниц из корзины), очистка опасного HTML и адресов, права на отдельные страницы, медиатека (загрузка, дедупликация, SVG, защита от удаления используемых файлов), импорт страниц, `/health`, заголовки, лимиты тела, фоновый вебхук, 404 на невалидные адреса.

## Контракт

Пакет `@crito/contract` (`packages/contract`) описывает формат данных между API, админкой и сайтами: страница и блоки (`ContentPage`, `ContentBlock`), манифест (`BlockManifest`, `JsonSchema`), запросы и ответы API, права (`Grant`), формат файла экспорта.

- **Только типы.** Подключается без сборки через `import type`; рантайм-значений в нём быть не должно (сборки API и админки не найдут его в рантайме).
- **Один источник правды.** DTO в API объявлены как `implements` интерфейсов контракта, тела запросов в админке проверяются через `satisfies`.
- **Ответы API сверяются с контрактом на уровне типов** в `apps/api/test/contract.check.ts` (даты как строки; JSON-поля `blocks` и `meta` исключены, их форму гарантирует проверка по манифесту). Если ответ сервиса перестал совпадать с контрактом, `npm run typecheck` падает.
- Меняя формат данных, начинайте с контракта, затем чините то, на что укажет `npm run typecheck`.
